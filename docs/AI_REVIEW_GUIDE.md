# BobFull 담당자 AI PR 검토·리뷰 반영 가이드

## 1. 역할

이 문서는 PR 담당자의 AI가 자신의 연결 PR을 검토하고, 담당자 Human 답변을 보완하며, PR에 등록된 리뷰·댓글의 반영 여부를 판단할 때 사용하는 기준이다.

별도의 다른 팀원 AI 리뷰는 BobFull 워크플로우의 공식 단계나 필수 조건으로 관리하지 않는다. PR에 리뷰·댓글이 등록되면 작성 주체와 관계없이 참고 입력으로 읽는다.

담당자 AI의 검토는 다음을 수행한다.

- 최신 Head의 실제 Diff 자체 검토
- Issue 댓글의 최종 계약·현재 상태 Label·PR 설명 정합성 확인
- 테스트·build·직접 검증 증거 확인
- 담당자 Human 이해도 1차 답변 검증과 `AI 기준 답변` 작성
- Human 리뷰 확인
- 등록된 리뷰·댓글의 근거 확인과 범위 안 수정

담당자 AI는 Approve와 Merge를 수행하지 않으며 Human 코드 리뷰를 대체하지 않는다.

## 2. 실행과 시작 조건

연결된 PR의 검토·리뷰 반영에는 다음 명령을 사용한다.

```text
PR #번호 검토하라
```

담당자 AI는 PR 번호로 연결된 모든 Issue, 각 Issue 댓글의 최종 계약, 현재 `status:*` Label과 PR 상태를 읽고 PR 검토·리뷰 반영 단계부터 재개한다.
PR 답변 또는 Human 리뷰 작성 후 `Issue #번호 구현하라`를 다시 입력하도록 요구하지 않는다.
실제 상태는 GitHub `status:*` Label 하나로만 관리하며, 상태 전환 전 기존 `status:*` Label을 모두 제거하고 새 Label 하나만 적용한다.

### 최소 검토 조건

다음 세 가지를 확인할 수 있으면 현재 상태와 관계없이 검토한다.

1. 최신 Head Commit SHA
2. 최신 Head의 실제 Diff
3. 해당 PR의 연결된 모든 Issue 또는 작업 범위

다음 상태는 검토 중단 사유가 아니다.

- PR이 Draft 또는 구현 중임
- Issue 댓글의 최종 계약 기록 또는 상태 Label이 미완료임
- 테스트·build가 실패함
- 테스트·직접 검증·CI가 미실행임
- `FAIL`, `HOLD`, `NOT_RUN`이 존재함
- 담당자 Human 답변이 미작성·불완전·`모름`임
- Human 리뷰가 미작성 또는 이전 Head 기준임
- 다른 리뷰·댓글이 없음
- PR 설명과 실제 Diff가 불일치함

이러한 항목은 현재 결함·확인 필요·미검증 위험으로 기록한다.

최신 Head SHA, 실제 Diff 또는 작업 범위를 확인할 수 없을 때만 검토 준비 미완료로 보고한다.

## 3. 검토 입력

가능한 범위에서 다음을 확인한다.

- 연결된 모든 Issue의 최종 계약
- 담당자 AI가 각 Issue 댓글에 남긴 최종 계약과 `status:in-progress` 기록
- 최종 계약 이후 변경 여부
- PR 본문
- 최신 실제 Diff
- 관련 코드와 테스트
- 테스트·build·직접 검증·CI 증거
- 미검증 범위와 남은 위험
- 담당자 Human 이해도 답변
- PR 댓글의 Human 리뷰 의견
- PR의 Review·Conversation 댓글·inline comment

리뷰·댓글의 작성자가 Human인지 AI인지에 따라 우선순위를 자동으로 정하지 않는다. 실제 코드·계약·테스트 근거로 판단한다.

## 4. 코드와 계약 검토

### 기본 검토

- 연결된 모든 Issue의 범위·제외 범위·완료 조건
- 각 Issue 댓글의 최종 계약과 `status:in-progress` 기록의 연결
- 최종 계약 이후 변경 여부
- 요청부터 응답·저장까지 실제 코드 흐름
- 입력 검증과 예외 처리
- 코드와 PR 설명의 일치
- PR 본문의 변경 범위·변경 파일·검증 기록이 최신 실제 Diff와 실행 결과에 일치하는지
- 테스트와 완료 조건의 연결
- 실제 실행 결과와 미검증 범위
- 범위 밖 변경과 불필요한 복잡성
- 비밀정보·개인정보 포함 여부

### 강화 검토

인증·결제·예약·좌석·상태 변경·정산·외부 연동에는 다음을 추가한다.

- 구현 전 `AI_IMPLEMENTATION_GUIDE`의 설계 확인이 수행됐는지 확인한다.
- Draft PR 생성 후 PR Conversation 댓글에 아래 `구현 전 설계 확인 기록`이 남았는지 확인한다. Issue 댓글과 PR 본문은 이 기록의 위치가 아니다.
- 사전 확인 내용과 최신 Diff가 다르면 변경된 이유와 최종 구조가 기록됐는지 확인한다.
- 인증·인가·소유권
- 트랜잭션·Rollback·부분 성공
- 상태·금액·수량 정합성
- 중복 요청·멱등성
- 동시성·락·재시도
- 외부 연동 실패와 보상

```markdown
## 구현 전 설계 확인 기록

- 책임 클래스:
- 상태 변경 위치:
- 트랜잭션 범위:
- 실패 처리 방식:
- 담당자 Human 확인: `확인 | 수정 요청`
- 구현 중 달라진 점: `없음 | 변경 내용과 이유`
```

## 5. 담당자 Human 이해도 검토

담당자 Human은 PR 본문의 1차 답변과 최종 확인을 직접 작성한다. 1차 답변은 `모르겠습니다`여도 된다.

### 질문 생성 기준

Human 이해도 질문의 목적은 담당자가 반영할 코드의 핵심 개념과 요청 흐름을 이해했는지 확인하는 것이다. 프레임워크 내부 구현, 라이브러리 호환성·선택, 암호화 세부 구현, 특정 클래스·메서드 또는 호출 순서의 암기를 시험하지 않는다.

- 기본 검토는 1~2개, 강화 검토는 2~3개 질문을 작성한다. 강화 검토는 코드·계약·검증 범위를 높이는 것이며 질문 난이도를 높이는 의미가 아니다.
- 모든 질문은 신입 백엔드 기술면접 기본 개념 수준으로, 코드 탐색 없이 30초~1분 안에 답할 수 있어야 한다. 기본 개념을 묻고 현재 BobFull 적용을 짧게 연결한다.
- 질문 하나에는 독립된 면접 주제 하나만 포함한다. 인증과 인가 또는 401과 403처럼 하나의 비교 주제는 허용한다.
- 허용 질문은 난이도 판단 예시이며 고정 목록이 아니다. 실제 질문은 대상 Issue·PR의 핵심 개념과 현재 작업 범위를 기준으로 새로 작성한다.

허용 예시:

- 인증과 인가는 무엇이 다른가요?
- JWT를 사용하는 이유는 무엇인가요?
- 401과 403은 무엇이 다른가요?
- 비밀번호를 평문으로 저장하면 안 되는 이유는 무엇인가요?
- 구체적인 경로 규칙을 넓은 규칙보다 먼저 선언하는 이유는 무엇인가요?
- 이번 Issue에서 인증 실패 시 어떤 상태 코드를 반환하나요?

다음 중 하나라도 해당하면 Human 이해도 질문으로 사용하지 않고 더 쉬운 질문으로 재작성한다.

- 특정 클래스·메서드 이름, Spring Security 필터 내부 호출 순서, 여러 프레임워크 컴포넌트의 연쇄 동작을 알아야 답할 수 있음
- 라이브러리 버전·의존성 호환성 또는 암호화 알고리즘 직접 구현 세부를 물음
- 코드를 열어봐야 답할 수 있음
- 요청 흐름, 프레임워크 내부 동작, 라이브러리 선택처럼 서로 독립된 주제를 한 질문에 함께 요구함
- 구현자·설계자·시니어 리뷰어에게 적합한 질문임

질문을 출력하기 전에 다음을 확인한다.

1. 신입이 기본 개념 학습만으로 답할 수 있는가
2. 1분 이내에 답할 수 있는가
3. 특정 클래스·메서드 이름을 몰라도 되는가
4. 독립된 면접 주제 하나만 포함하는가(하나의 비교 주제는 허용)
5. 코드 탐색 문제가 아니라 기술면접 질문인가

하나라도 충족하지 못하면 해당 질문을 폐기하고 더 쉬운 질문으로 다시 작성한다. 담당자가 `모르겠습니다` 또는 `추가 설명 필요`라고 답하면 AI가 기본 개념을 쉬운 말로 설명하고, 같은 개념의 더 쉬운 질문으로 한 번만 재확인한다. 고급 설계 내용을 새 이해도 질문으로 추가하지 않으며, 필요한 고급 검토는 AI 리뷰 결과, 구현 선택과 근거, 위험·트레이드오프, ADR 필요 여부 또는 추가 Human 설계 검토로 분리한다.

담당자 AI는 각 1차 답변을 최신 코드와 비교하고 다음을 작성한다.

```markdown
**AI 답변 검토:** `일치 | 보완 필요 | 미작성`

**AI 기준 답변:**
```

판단 기준:

- 정확함: `일치`
- 핵심 흐름·예외·테스트 설명이 부족함: `보완 필요`와 `AI 기준 답변`의 보완 근거
- 실제 코드와 다름: `보완 필요`와 코드 근거
- 답변 없음: `미작성`

AI 기준 답변은 절대적인 모범 답안이 아니라 현재 확정 계약·최신 Diff·코드·문서·테스트에 근거한 설명이다. 담당자 AI는 Human 답변 원문과 최종 확인을 수정하거나 대신 작성하지 않는다. 점수·합격·불합격 형식은 사용하지 않는다.

기본 검토에서는 AI 기준 답변 뒤 Human이 `이해함`을 선택하면 답변 재작성을 요구하지 않는다. 강화 검토 대상은 이 문서의 §4 강화 검토 기준만 따르며, `이해함` 외에 담당자가 직접 작성한 이해 근거 한 줄 이상이 필요하다. `추가 설명 필요`면 AI가 근거를 보완하고, `동의하지 않음`이면 다음 단계로 진행하지 않고 Human 판단을 요청한다.

다른 리뷰어 또는 다른 AI는 이 Human 이해도 답변을 보완하는 공식 역할을 갖지 않는다. 해당 보완은 담당자 AI의 책임이다.

이 규칙은 담당자 Human 이해도에만 적용한다. 독립 Human 리뷰는 PR 본문 마지막의 PR별 `Human Review Checklist`를 참고하거나 복사한 PR 댓글로 남긴다. 이해 확인이 완료돼도 담당자 AI는 최신 Diff와 검증을 계속 확인하고, 남은 BLOCKER가 없을 때만 `status:final-human-review`를 적용한다. Ready 전환·Approve·Merge는 Human 책임이다.

## 6. Human Review Checklist와 댓글 확인

담당자 AI는 Draft PR 본문 마지막에 연결 Issue의 최종 결정·완료 조건, 최신 실제 Diff, 추가·수정 테스트와 실제 테스트 결과를 근거로 PR 전용 `Human Review Checklist`를 작성한다. 구현 확인과 테스트 확인을 분리하고, 코드와 테스트에서 실제로 확인 가능한 동작만 한 항목씩 작성한다. 범위 밖 기능·미구현 내용·추상적 문구·불필요하게 긴 항목은 제외한다.

Human 리뷰어는 PR 본문을 수정하지 않고 체크리스트를 참고하거나 복사해 PR 댓글에 체크 여부와 의견을 직접 작성한다. 리뷰어와 리뷰 시각은 GitHub 댓글 메타데이터를 사용하며, 체크리스트 댓글에 기준 Head SHA를 기록하거나 추정하지 않는다.

담당자 AI는 댓글의 체크 여부와 의견을 작성하거나 수정하지 않는다. 최신 Diff를 기준으로 추가 설명 요청과 문제 제기를 대조해 실제 결함·테스트 공백·계약 충돌인지 판단한다. 새 Commit 이후 정식 Approve의 유효성은 GitHub Branch Ruleset의 `dismiss_stale_reviews_on_push: true` 설정으로 관리하며, 담당자 AI는 PR 검토 명령마다 최신 Diff를 다시 확인한다.

## 7. PR 리뷰·댓글 판단

PR에 등록된 모든 리뷰·댓글은 선택적 참고 입력이다. 특정 리뷰가 있어야 검토나 수정 단계가 시작되는 것은 아니다.

각 의견은 다음으로 분류한다.

### 명확한 결함

조건:

- 실제 코드·Issue 계약·테스트 근거가 있음
- Issue 범위 안에서 수정 가능함
- 정책 재결정이 필요하지 않음

처리:

- 실제 파일 수정 시작 전 연결된 모든 Issue의 기존 `status:*` Label을 제거하고 `status:in-progress` 하나 적용
- 수정
- 영향받는 테스트·build·직접 검증 재실행
- PR 기록 갱신

PR을 읽고 보고만 할 때는 기존 Label을 유지한다. 수정·검증·Push·최신 Head 자체 검토가 끝나면 연결된 모든 Issue의 기존 `status:*` Label을 제거하고 `status:final-human-review` 하나만 적용한다.

### 설명 또는 확인 요청

조건:

- 결함으로 단정되지 않음
- 코드 흐름이나 테스트 범위 설명이 필요함

처리:

- 확인 결과와 코드 근거 기록
- 임의 코드 수정하지 않음

### Human 결정 필요

조건:

- 정책·API·DB·상태·권한·트랜잭션 재결정
- 다른 담당자 계약 변경
- 범위 확장 또는 새로운 기술 도입

처리:

- 수정하지 않음
- Human 결정 요청

### 미반영

조건:

- 근거를 확인할 수 없음
- Issue 범위 밖임
- 이미 해결됐거나 현재 Head에 적용되지 않음

처리:

- 반영하지 않은 이유 기록

## 8. 발견 사항 기준

실제 근거가 있을 때만 발견 사항으로 기록한다.

- **BLOCKER**: 보안·데이터·정합성·핵심 계약 훼손 위험
- **MAJOR**: 요구사항 실패·높은 확률의 런타임 오류·필수 실패 처리 누락
- **MINOR**: 제한된 유지보수성·명확성·테스트 공백
- **QUESTION**: 결함으로 단정할 수 없고 Human 결정이 필요한 사항

근거 없는 추측, 개인 취향, Issue 밖 미래 기능과 무관한 리팩터링은 지적하지 않는다.

## 9. 담당자 AI 검토 결과 기록

PR 본문의 `담당자 AI 검토·수정 기록`에 다음을 작성한다.

```markdown
## 담당자 AI 검토·수정 기록

- 담당자 AI 검토 기준 Head:
- 담당자 AI 검토 결과: `수정 필요 | 확인 필요 | 특이사항 없음`
- 확인한 PR 리뷰·댓글:
- 반영한 항목:
- 반영하지 않은 항목과 이유:
- Human 결정이 필요한 항목:
- 재실행 테스트·build 결과:
- 최신 Head SHA:
- 남은 미검증 위험:
```

검토 결과가 `특이사항 없음`이어도 확인 범위와 미검증 위험을 기록한다. 이 결과는 독립 승인이나 Merge 가능 판정이 아니다.

## 10. 최신 Head 재검토

수정 Commit이 올라오면 이전 결과를 그대로 재사용하지 않는다.

- 현재 Head SHA와 수정 Diff 확인
- 기존 지적 해결 여부 확인
- 영향받은 테스트·build·직접 검증·CI 확인
- 새 결함과 PR 설명 불일치 확인
- 담당자 Human 답변과 AI 기준 답변 재대조
- PR 댓글의 Human 리뷰 의견과 최신 Diff의 대조
- 남은 PR 리뷰·댓글 확인

Human 리뷰 댓글의 작성 시점과 무관하게 담당자 AI는 현재 최신 Diff를 기준으로 다시 검토한다.

## 11. Merge 전 경계

다음이 충족돼야 담당자 AI가 연결된 모든 Issue에 `status:final-human-review`를 적용하고 Human 최종 리뷰를 요청할 수 있다.

- 담당자 Human 답변과 AI 검토 완료
- 필수 테스트·build·직접 검증 결과 확인
- 최신 Head 기준 담당자 AI 검토 완료
- 해결되지 않은 BLOCKER 없음
- 남은 Human 결정 필요 사항 명시
- `DOMAIN_DEPENDENCIES.md` §5 정책 변경 영향표에 해당하는 변경은 §6의 관련 체크 항목을 구현·PR 검토에서 확인
- 기존 최종 계약 안에서 수정 가능한 미해결 항목은 `status:in-progress`에서 수정·재검증하고, 새로운 Human 결정이 필요한 경우에만 `status:human-answer-required`로 전환

`status:final-human-review`는 Human 리뷰를 기다리는 상태이므로 Human 리뷰의 최신 Head 재확인은
이 Label을 적용하는 선행 조건이 아니라 Ready 전환과 Merge 전 확인 조건이다.

GitHub Rules의 Human 리뷰·Approve 조건과 Merge 결정은 Human이 담당한다.

## 12. 금지 사항

담당자 AI는 다음을 수행하지 않는다.

- Human 답변 또는 Human 리뷰 대리 작성
- 근거 없는 리뷰 의견 자동 반영
- 정책·API·DB·권한·트랜잭션 임의 결정
- Approve
- Merge
