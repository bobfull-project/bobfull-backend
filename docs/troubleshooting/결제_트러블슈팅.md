결제 도메인에서 확인한 문제와 검증 상태를 기록한다.

## 1. `paymentId` 내부 PK와 외부 식별자 분리

> DB 내부 식별자와 PortOne·외부 API 식별자를 분리해 외부 연동 규칙을 DB PK에 결합하지 않는다.

### 상태: 설계 반영

- `설계 반영`

### 판단

- DB 내부 PK는 `Long` 자동 증가 식별자를 사용한다.
- PortOne 결제 요청·조회와 외부 API에는 UUID 기반 `String paymentId`를 사용한다.
- `paymentId`에는 UNIQUE 제약을 적용한다.
- 구체적인 접두사와 문자열 형식은 선택 PG의 길이·허용 문자 조건을 구현 시 확인한다.

## 2. 좌석 선점 만료와 PG 결제 승인 시점 불일치

> 내부 좌석 선점은 10분 후 만료되지만 PG 결제가 이후 승인될 수 있어, 결제는 됐는데 예약은 실패하는 문제가 발생할 수 있다.

### 상태: 부분 해결·운영 보상 필요

- `검토 중`

### 문제 상황

- 밥풀은 예약 준비 시 좌석을 10분간 선점한다.
- PortOne·PG 결제 승인 시점은 내부 `expiresAt`과 별개로 동작할 수 있다.
- 사용자가 만료 직전에 결제를 시작하면 내부 만료 이후 외부 결제가 승인될 수 있다.
- 서버는 예약을 확정할 수 없지만 결제는 승인된 상태가 될 수 있다.
- 즉시 취소를 요청하더라도 카드 취소 반영이 지연될 수 있어 사용자 경험이 나빠진다.

### 원인

- 내부 좌석 선점 만료와 PG 결제 승인 시점은 서로 독립적이다.
- 프론트 타이머는 신규 결제 시작은 막을 수 있지만 이미 열린 결제창과 외부 인증 과정까지 완전히 제어하지 못한다.
- 자동 승인 방식에서는 결제 승인 직전에 서버가 좌석 상태와 `expiresAt`을 최종 검증하기 어렵다.

### 검토한 해결 방법

#### 방법 1. 프론트 타이머로 10분 이후 결제 차단

- 10분 이후 버튼 비활성화와 신규 결제창 호출 차단은 가능하다.
- 이미 열린 결제창 또는 진행 중인 외부 인증까지 완전히 막지는 못한다.
- 결론: 보조 수단이지 근본 해결이 아니다.

#### 방법 2. 만료 후 승인된 결제를 즉시 취소

- 예약 확정은 거절하고 결제를 즉시 취소할 수 있다.
- 사용자는 결제 승인 후 취소 반영을 기다려야 할 수 있다.
- 결론: 보상 수단이며 사용자 경험 문제를 완전히 해결하지 못한다.

#### 방법 3. PortOne V2 수동 승인 검토

- 사용자의 PG 인증이 끝난 뒤 실제 승인 전에 서버가 `expiresAt`과 좌석 상태를 최종 확인한다.
- 유효하면 서버가 승인 API를 호출한다.
- 만료됐거나 좌석이 없으면 승인하지 않는다.
- 결론: 현재 가장 적합한 후보안이다.

### 남은 검증 항목

- [ ] 사용할 PG 채널이 PortOne V2 수동 승인을 지원하는지 확인
- [ ] 테스트 채널에서 수동 승인 흐름 검증
- [ ] 인증 후 전달되는 paymentToken 또는 승인용 식별자 확인
- [ ] 인증 후 승인 가능한 제한 시간 확인
- [ ] 서버 승인 API 연동 방식 확인
- [ ] 만료·좌석 부족 시 미승인 처리 확인
- [ ] 완료 API·웹훅 구조와의 정합성 검토
- [ ] 자동 승인 방식과 수동 승인 방식의 트레이드오프 비교
- [ ] 취소 반영 지연이 실제 사용자 경험에 미치는 영향 확인

### #93 반영 사항

- `PaymentStatus.EXPIRED`와 멱등 도메인 메서드 `expireIfNeeded(now)`를 추가했다. `READY && expiresAt <= now`에서만 EXPIRED로 전이한다.
- 완료 API는 EXPIRED 또는 만료 READY를 `409 PAYMENT_EXPIRED`로 거절한다. 완료 처리 중 EXPIRED로 바꾼 뒤 예외를 던져 트랜잭션 롤백으로 정규화가 사라지는 방식은 사용하지 않는다.
- 좌석 계산은 `expiresAt`을 직접 기준으로 하므로 스케줄러 실행 전에도 만료 READY를 제외한다. 스케줄러는 60초 fixed delay, 100건 batch로 상태만 EXPIRED로 정규화한다.
- 웹훅은 PortOne 재조회 뒤 외부 PAID·내부 EXPIRED 또는 만료 READY를 만나면 상태 전이·예약 확정을 수행하지 않고 `PAYMENT_COMPENSATION_REQUIRED` 구조화 로그를 남긴 뒤 200으로 확인한다.
- 자동 결제 취소·환불·보상 트랜잭션은 구현하지 않았다. 운영자가 구조화 로그로 수동 처리 대상을 확인한다.

### 현재 판단

PortOne V2 수동 승인을 우선 해결 후보로 검토한다. 실제 PG 지원 여부와 테스트 결과를 확인하기 전에는 최종 해결로 확정하지 않는다. 구현 전 예상 위험이므로 `검토 중`으로 기록하며, #92·#93 구현 과정에서 실제 결과와 테스트 근거를 추가한다.

### 스케줄러가 다루는 범위

- 결제하지 않고 이탈해 완료 API가 오지 않은 READY Payment를 `EXPIRED`로 정규화한다. 좌석은 별도 복구 호출이 아니라 `expiresAt` 계산으로 이미 반환된다.
- 내부 만료 뒤 외부 결제가 승인되어 결제와 예약 결과가 갈라지는 문제는 스케줄러만으로 해결하지 못한다.

### 관련 작업: 만료와 승인 시점

- #92 PortOne V2 결제 검증 및 완료 처리 구현

## 3. PortOne SDK 동기 대기와 외부 API 예외 변환 미검증

> PortOne 결제 단건 조회의 동기 대기와 외부 API 오류 변환 정책은 실제 연동 환경에서 아직 검증되지 않았다.

### 상태: 검토 중

- `검토 중`

### 문제 상황

- `PortOneSdkPaymentReader.read(...)`는 PortOne SDK의 비동기 결제 단건 조회 결과에 `join()`을 호출해 동기적으로 응답을 기다린다.
- 밥풀 애플리케이션은 별도 타임아웃 값을 직접 설정하지 않는다. 현재 사용하는 `io.portone:server-sdk:0.24.0`의 `PortOneClient`는 내부 HTTP Client에 request/connect/socket timeout을 각각 60초(60,000ms)로 설정한다.
- 현재 `PortOneClient` 생성자는 API Secret, API Base, Store ID만 받으며, 프로젝트가 사용자 정의 HTTP Client나 타임아웃 값을 바로 전달하는 설정은 노출하지 않는다.
- 실제 PortOne API 오류가 어떤 SDK 예외로 반환되는지는 실제 연동 테스트로 확인하지 않았다.
- `PortOneSdkPaymentReader`는 SDK 호출 예외를 잡아 `PaymentErrorCode` 기반 `CustomException`으로 변환하지 않는다.

### 현재 위험

- PortOne 응답이 지연되면 완료 API 요청 스레드가 장시간 대기할 가능성이 있다.
- 외부 연동 오류는 서비스 계층에서 구분되지 않는다. 현재 `GlobalExceptionHandler`의 일반 예외 처리에 따라 `INTERNAL_SERVER_ERROR` 응답으로 처리된다.
- 결제 미존재, 인증 오류, 네트워크 장애, 외부 서버 오류를 구분하지 못할 가능성이 있다.
- 재시도 가능한 오류와 재시도하면 안 되는 오류의 정책이 아직 명확하지 않다.
- 현재 일반 예외 응답은 `INTERNAL_SERVER_ERROR`로 고정되지만, 원인 분류와 로그 보존을 위한 외부 예외 변환 경계가 필요하다.

### 검토할 해결 방향

- 외부 결제 조회의 최대 대기 시간 정책을 정의한다.
- 타임아웃, 연결 실패, 인증 오류, 결제 미존재, 외부 서버 오류를 분류한다.
- PortOne SDK 예외를 내부 `PaymentErrorCode` 기반 예외로 변환한다.
- 내부 로그에는 원인을 보존하고 클라이언트에는 안전한 오류 응답만 제공한다.
- SDK 호출에 `join()`을 사용한다고 자동 재시도가 적용되지는 않는다. 타임아웃과 재시도는 별개의 정책이므로, 재시도가 필요하면 대상 예외·횟수·간격을 별도로 결정한다.
- 실제 PortOne 테스트 환경에서 SDK 예외 구조를 확인한다.

### 남은 검증 항목

- [ ] 정상 결제 단건 조회
- [ ] 존재하지 않는 paymentId 조회
- [ ] 잘못된 PortOne API Secret
- [ ] 네트워크 연결 실패
- [ ] PortOne 서버 오류 응답
- [ ] 응답 지연 또는 무응답 시 처리
- [ ] SDK가 반환하는 실제 예외 타입과 감싸진 원인 확인
- [ ] 외부 예외의 내부 PaymentErrorCode 변환
- [ ] 클라이언트 응답에 SDK 내부 정보가 노출되지 않는지 확인
- [ ] 재시도 가능 여부와 재시도 횟수 정책 검토

### 현재 판단

현재 PortOne SDK 호출은 정상 응답을 기준으로 구현돼 있으며, SDK 내부 기본 타임아웃은 확인했지만 실제 외부 API 장애·지연과 예외 변환은 검증되지 않았다. 타임아웃과 재시도·예외 변환 정책은 실제 SDK 응답 및 테스트 환경 확인 후 결정하며, 자동 취소·환불·보상도 해결되지 않았다. 그전까지는 검토 중 위험으로 유지한다.

## 4. 락 획득 후 Payment 만료 재검증

> 외부 조회와 락 대기 뒤 실제 상태 변경 직전에 만료를 다시 확인해, 이미 만료된 READY Payment가 PAID로 처리되는 경쟁 조건을 막는다.

### 상태: 해결 및 검증 완료

- `해결 및 검증 완료`

### 문제 상황

결제 완료 흐름은 두 단계로 분리된다.

1. `PaymentCompletionService`에서 기본 검증과 PortOne 재조회를 수행한다.
2. `PaymentCompletionTransactionService`에서 비관적 락을 획득하고 PAID 전환을 수행한다.

최초 만료 검사와 실제 상태 변경 사이에는 PortOne 응답 대기와 DB 락 대기 시간이 존재한다. 그 사이 Payment가 만료될 수 있으므로, 최초 검사만 통과한 뒤 상태를 변경하면 이미 만료된 READY Payment를 PAID로 처리할 수 있는 TOCTOU 경쟁 조건이 있었다.

### 해결

`PaymentCompletionTransactionService.complete()`는 락 획득 직후 `Clock`으로 기준 시각을 한 번 생성하고, 그 시각으로 `expiresAt`을 다시 검증한다. 같은 기준 시각을 만료 여부와 `paidAt`에 함께 사용해 한 완료 처리 안에서 시간 판정과 기록이 서로 달라지지 않게 했다.

락 획득 뒤 만료가 확인되면 `Payment.complete()`와 `ReservationConfirmationPort.confirm()`을 실행하지 않는다. 완료 API는 `PAYMENT_EXPIRED`로 거절하며 Payment 상태 정규화는 만료 Processor가 담당한다.

### 검증 근거

- `PaymentCompletionTransactionServiceTest`의 `락_획득_대기중_만료된_Payment은_READY를_유지하고_Port를_호출하지_않는다`는 고정 `Clock`으로 락 대기 중 만료 경계를 재현해 READY 유지와 Port 미호출을 검증한다.
- #93에서는 Payment 완료·예약 확정 단일 트랜잭션, 반복·동시 요청, MySQL 행 락과 만료 Processor 경쟁을 추가로 검증한다.

### 관련 작업

- Issue #92 PortOne V2 결제 검증 및 완료 처리 구현
- PR #101 PortOne V2 결제 검증 및 완료 처리

### 교훈

외부 API 호출이나 락 대기 뒤 상태를 변경할 때는, 최초 검증 결과만 신뢰하지 말고 최신 상태를 다시 검증해야 한다.

## 5. 웹훅 서명 경계와 외부 PAID·내부 EXPIRED 관찰

> 웹훅은 인증 없이 도달할 수 있어도, 검증 전 JSON 해석이나 결제 처리에 진입하면 안 되며 외부 승인과 내부 만료가 갈라지면 운영 보상 대상이 된다.

### 상태: 구현·테스트 반영, 실제 PortOne 전달 NOT_RUN

- `/api/webhooks/portone`은 SecurityConfig의 `permitAll`과 JWT 필터 제외 경로다. 이는 PortOne 호출을 받기 위한 진입 정책이며 신뢰 결정은 아니다.
- Controller는 원본 Body 및 `webhook-id`, `webhook-signature`, `webhook-timestamp`를 `PortOneWebhookVerifier`로 검증한 뒤에만 `Transaction.Paid` 이벤트의 paymentId를 공통 완료 처리에 전달한다.
- 헤더 누락·서명 실패는 400이고 Payment 조회·PortOne 재조회·상태 전이·예약 확정을 호출하지 않는다. 미지원 이벤트와 알려진 영구 업무 실패는 200, PortOne 네트워크·DB·미지의 서버 오류는 5xx다.
- 외부 PAID·내부 EXPIRED/만료 READY는 `event=PAYMENT_COMPENSATION_REQUIRED`, `paymentId`, `externalStatus`, `internalStatus`, `expiresAt`, `reason`을 기록한다. 자동 취소·환불은 후속 범위다.

### 미검증

- 로컬 `.env`의 PortOne 필수 환경변수 존재와 local 설정 바인딩은 값 비노출 방식으로 확인한다. 실제 PortOne 테스트 채널의 웹훅 전달은 외부 공개 URL과 채널 발송 절차가 준비되지 않아 `NOT_RUN`이다.
- Controller의 HTTP 헤더·Security 경계와 SDK Adapter 호출 인자는 WebMvc·Security 및 단위 테스트로 검증한다. 실제 채널의 정상 서명, 실제 재조회, SDK 예외 매핑은 외부 공개 URL·채널 발송이 준비된 뒤 확인한다.
